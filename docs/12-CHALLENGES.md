| # | Date | Part | What went wrong | How we found / fixed it | What we learned |
|---|---|---|---|---|---|
| C1 | 2026-09-27 | B (setup) | The laptop only had the .NET 8 SDK, but the API targets .NET 10. Microsoft's `dotnet-install.ps1` downloaded .NET 10 fine but failed while unzipping: *"cannot access `dotnet.exe` because it is being used by another process"*. | Listed the running `dotnet.exe` processes (`Get-CimInstance Win32_Process`): two `dotnet run` servers from another project had been open since the night before and were locking the file. Rather than kill someone else's servers, we unzipped the downloaded SDK ourselves and skipped files that already existed (only the `dotnet.exe` launcher). `dotnet --list-sdks` then showed 8.0.425 and 10.0.401. | `dotnet.exe` is only a small launcher that hands over to the newest .NET version installed next to it, so several SDKs live side by side. Check tool versions on day one, and read the actual error before retrying. |
| C2 | 2026-09-28 | Shared (API) | While testing login with a broken request body, the API answered with raw .NET parser text: *"The JSON value could not be converted to System.String. Path: $.nic…"* — not the human-friendly message our rules promise. | Found by deliberately sending wrong/missing JSON during Phase 2 testing (not just the happy path). Fixed the 400 handler in `Program.cs` to name the bad field in plain words ("The value of 'nic' is not in the right format."). | Test the error paths, not only the success paths — framework defaults can leak technical text to users. |
| C3 | 2026-09-28 | B (API) | A build during Phase 3 reported "2 errors", yet the commit went ahead: the check only looked for the word "Error(s)", not for **0** errors. The errors were `MSB3027: file is locked by SunShare.Api` — Kvn's own `dotnet run` (from trying Swagger) was still running and holding `bin\SunShare.Api.exe`. | Read the full build output; found the running process with `Get-CimInstance Win32_Process` (it was Kvn's, so it was left alone). Built into a separate output folder (`-p:OutDir=...`) to prove the code itself compiled (0 errors, 0 warnings), and tested on a second port (5081). Replaced the loose check with a strict one that stops unless both counts are 0. | A running app locks its own files on Windows — stop it (Ctrl+C) before building. And a check must test for success, not just for the presence of a summary line. |
| C4 | 2026-09-29 | B (hosting) | First IIS deploy: every request gave **HTTP 500.19 (0x80070021)** "This configuration section cannot be used at this path… locked at a parent level", pointing at `<modules><remove name="WebDAVModule" />` in our `web.config`. | Read IIS's detailed error page (curl on the laptop shows full details). IIS's server-wide `applicationHost.config` locks the `<modules>` section, so a site may not change it. WebDAV isn't even installed on the laptop, so we removed the `<modules>` block and kept only `<handlers><remove name="WebDAV" />`. Redeployed; proved PUT/PATCH/DELETE reach the API (our own 400/403/404, no 405). | Copy-pasted "best practice" config can clash with the server's locks. Read the exact error code, fix the smallest thing, then prove the original goal (no 405) still holds. |
| C5 | 2026-09-29 | B (setup) | After installing the Hosting Bundle, new terminals would say "No .NET SDKs were found": it put a **runtime-only** `C:\Program Files\dotnet` on the *system* PATH, which Windows searches before the *user* PATH where our SDK lives. | Checked both PATH lists and the installed runtimes/SDKs with PowerShell. The deploy script now looks for a `dotnet` that actually has an SDK; the permanent fix is installing the SDK next to that runtime (`winget install --id Microsoft.DotNet.SDK.10 -e`). | Installers change PATH; the first match wins. When a command suddenly "forgets" something, check which copy of the program is running. |
| C6 | 2026-09-29 | A (web) | Two redirect bugs found while clicking through the new Login page: (1) after logging in from a deep link (e.g. `/#/prosumers`) the app still went to the Dashboard; (2) after **Log out** from a Backoffice-only page, the next user (a Grid Operator) landed on that page and saw "no access". | Scripted login/logout runs in the browser showed the wrong final address. Cause: React Router changes pages inside a low-priority React *transition*, so a state change made at the same time (the user being saved / forgotten) re-rendered first and triggered a different redirect. Fixes: Login keeps a single redirect ("logged in → page asked for, else dashboard"); logout forgets the user and navigates inside the same `startTransition`, so both happen in one step. Re-tested all four paths. | When two things change "at the same time" in React, their order can differ from the code order. Test the unhappy paths (deep links, switching users), not only a clean login. |
| C7 | 2026-09-29 | B (setup) | Could not create the Google Maps API key: Google Cloud needs a billing account, and the card authorization hold was more than Kvn could cover. A Google AI Studio key was suggested but only works for the Gemini AI service, not Maps. | Checked the rubric: 5 marks need "nearby stations on a map with details" (any map), 3 need a real Google map. Decided (D47): build the map screen last, try to get a key from someone with a card (key locked to our package + SHA-1, free Android map loads, $1 budget alert), otherwise use an OpenStreetMap map plus an "Open in Google Maps" hand-off. | External services can have non-technical blockers (money, accounts). Find out what is really marked, reorder work so the blocker isn't on the critical path, and prepare a fallback early. |
