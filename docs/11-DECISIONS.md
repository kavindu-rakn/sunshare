# 11 — Design & Development Decisions (log)

The brief asks us to **document design and development decisions** in the report, and the viva asks us to **justify** them. Add a row whenever something is decided or changed (newest at the bottom). Keep "Why" to one or two plain sentences.

| # | Date | Decision | Alternatives considered | Why |
|---|---|---|---|---|
| D1 | 2026-09-27 | Brand name **SunShare**, repo `sunshare` | HelioGrid, VoltSwap, solar-micro | Friendly and prosumer-focused: neighbours "sharing sunshine" |
| D2 | 2026-09-27 | API: **ASP.NET Core Web API on .NET 10 (LTS)**, controller style | .NET 8 (installed), minimal APIs | Brief requires C# Web API; .NET 10 is the current long-term-support version; controllers map cleanly to "one controller per resource" and are easy to explain |
| D3 | 2026-09-27 | Layers: **Controller → Service → MongoDbContext** (no repository layer) | Repository + Unit of Work | Services hold all business rules (FAT service); an extra repository layer adds files without adding understanding |
| D4 | 2026-09-27 | **MongoDB Community on the laptop** | MongoDB Atlas (cloud) | Demo/viva works without internet; campus Wi-Fi may block Atlas |
| D5 | 2026-09-27 | 4 collections named exactly like the rubric; **NIC as `_id`** for all users with a `role` field | Separate Prosumers collection | Rubric lists exactly four collections; brief makes NIC the primary key |
| D6 | 2026-09-27 | **JWT** login tokens + **BCrypt** password hashes | Sessions/cookies, plain passwords | Stateless tokens work the same for web and Android; never store plain passwords |
| D7 | 2026-09-27 | Web: **React (Vite) + JavaScript + Bootstrap 5**, HashRouter, `fetch` | React + Tailwind, Razor Pages, plain HTML | React is named in the brief and familiar; Bootstrap gives admin tables/forms fast and is marked in the rubric; HashRouter needs no IIS rewrite module |
| D8 | 2026-09-27 | Android: **Java + XML views**, minSdk 26 | Kotlin, Jetpack Compose | Java is closest to C#, so one coding style to explain; XML views are unmistakably "pure native" |
| D9 | 2026-09-27 | Android HTTP: **Retrofit + Gson** | Volley, HttpURLConnection | Industry standard, one line per endpoint, still native Android |
| D10 | 2026-09-27 | SQLite via **SQLiteOpenHelper** (no Room): tables `session`, `stations_cache`, `app_settings` | Room | Most literal match to "SQLite"; stores login details + reference data as the rubric asks |
| D11 | 2026-09-27 | **Reservations need staff approval** (Pending → Approved) before a QR exists | Auto-approve | Gives real "pending" data for the dashboards the rubric marks, and matches "once approved, the app generates a QR" |
| D12 | 2026-09-27 | QR contains `SUNSHARE|<reservationId>|<randomToken>`; token lives on the server | Signed JWT inside the QR | Simple and secure enough: nobody can fake a QR without the random token; easy to explain |
| D13 | 2026-09-27 | **"Nearby" distance is calculated in the API** (Haversine) | Calculate on the phone | FAT service: even this logic stays on the server; the phone only plots results |
| D14 | 2026-09-27 | API computes **`canModify`** for each reservation | Clients check the 12-hour rule themselves | Keeps the 12-hour rule in one place (API); clients just hide/show buttons |
| D15 | 2026-09-27 | Demo on **HTTP over LAN**; Android server address editable at runtime | HTTPS with a certificate; hard-coded IP | Certificates on IIS + Android add setup risk; editable address avoids rebuilding at the viva when the IP changes |
| D16 | 2026-09-27 | Work split **by feature** (Parts A–D), each end-to-end (API + web + mobile) | Split by layer | Matches how individual marks are given; each member explains one complete story |
| D17 | 2026-09-27 | AI coding assistants used (Claude Code, possibly Codex/Antigravity) under strict docs (`CLAUDE.md`), with rule tags and mandatory comments | No AI / unguided AI | Speed under a 3.5-day deadline while keeping code simple and explainable; disclosed in the report as the brief requires |
| D18 | 2026-09-27 | API docs page: **Swashbuckle Swagger UI**, replacing the .NET 10 template's `Microsoft.AspNetCore.OpenApi` package; Swagger stays on in every environment | Built-in OpenAPI (JSON only, no UI) + a separate UI package | The .NET 10 template makes only the JSON description; Swashbuckle adds the click-to-test page with an **Authorize** button for JWT in one package, and it is on our allowed list |
| D19 | 2026-09-27 | API runs on **plain HTTP only** (template's HTTPS profile and `UseHttpsRedirection` removed) | Keep HTTPS with a dev certificate | Matches D15: IIS and the phone use HTTP on the LAN; the redirect would only cause warnings and certificate problems |
| D20 | 2026-09-28 | **One branch + one pull request per phase**, reviewed by Kvn, merged with a merge commit; nothing committed straight to `main` | Commit straight to `main`; squash-merge PRs | The brief asks for meaningful commits and critically checked AI output — a PR per phase is a visible review step and a tidy page to link in the report; merge commits keep every commit and co-author trailer |
| D21 | 2026-09-28 | Android **Gradle build files in Kotlin DSL** (`*.gradle.kts`, Android Studio's default), while **all app code stays Java** | Groovy DSL (`build.gradle`) | It is Android Studio's default and recommended option; these files only configure the build (SDK versions, libraries) — they are not app source, so "no Kotlin source files" still holds |
| D22 | 2026-09-28 | Removed the Android template's example unit/UI tests and their test libraries (JUnit, Espresso) | Keep them | The rubric doesn't mark automated tests; we test through Swagger, the browser and the emulator (golden rule 8). Unused files and libraries would only need comments and explaining |
| D23 | 2026-09-28 | CORS: allowed list (5173, 8081) from `appsettings.json`; **in Development only**, any `localhost` port is allowed too | Fixed list everywhere; allow any origin | A preview browser or a second dev server may get a random port when 5173 is busy; production (IIS) stays strict, and outside sites are always blocked |
| D24 | 2026-09-28 | The API **starts even if MongoDB is down** (start-up DB work is logged, not fatal) and gives up on MongoDB after **5 seconds** (driver default is 30) | Crash on start; default 30 s timeout | `/api/health` can then honestly answer `503 "unreachable"` instead of IIS showing a 500.30 error page; a 5 s wait is much friendlier in the demo. Requests that hit the DB while it is down get `503 { message }` |
| D25 | 2026-09-28 | **Every** error uses `{ "message" }`: rule errors (`ApiException`), missing/expired token (401), wrong role (403), bad request bodies (400) and unexpected bugs (500, details only in the server log) | ASP.NET defaults (empty 401/403, ProblemDetails for 400) | Web and Android need one simple way to show errors: read `message`, show it |
| D26 | 2026-09-28 | JWT carries short claim names **`nic`, `name`, `role`** (`MapInboundClaims = false`, `RoleClaimType = "role"`) | .NET default long claim URLs (`http://schemas.microsoft.com/.../role`) | Easy to read on jwt.io at the viva and in code (`User.FindFirstValue("nic")`); `[Authorize(Roles = ...)]` still works |
| D27 | 2026-09-28 | Required/format checks for request fields live in the **services** (plain `if` + friendly message); ASP.NET's automatic "required" check is switched off, and unreadable JSON gets a friendly 400 | Data-annotation attributes (`[Required]`, `[EmailAddress]`) on DTOs | FAT service: all validation is in one place and every message is human-friendly ("Please enter the full name." instead of "The FullName field is required.") |
| D28 | 2026-09-28 | A slot's **time can't be changed once it has bookings** (409 "Add a new slot instead"); places and open/closed can still change | Move the bookings along with the slot | Booked prosumers chose that exact time, and each booking keeps a copy of it for the 7-day/12-hour rules (R9, R10); silently moving them would be unfair and would make those copies wrong |
| D29 | 2026-09-28 | **Renaming a station updates the `stationName` copies** in its bookings | Keep the old name in old bookings (pure snapshot) | Booking lists and the search box (Part D) match on `stationName`; stale names would look like a bug in the demo |
| D30 | 2026-09-28 | Malformed ids in URLs → **404**, and request times without a zone are taken as **UTC** | Let the driver throw (500); guess the laptop's time zone | Friendly, predictable answers for every client; the API never depends on the server's clock settings (IIS could run anywhere) |
| D31 | 2026-09-28 | Taking a slot place is **one conditional update** (`availableSlots > 0` in the filter + `$inc -1`); 0 matches → 409 "slot is full" | Read the slot, check in C#, then save | Check-then-save leaves a gap where two bookings both see the last place; MongoDB does the check and the subtraction in one atomic step. Tested: two parallel bookings for 1 place → one 201, one 409, never below 0 |
| D32 | 2026-09-28 | Saving an edit with **nothing changed** leaves the booking as it is (an Approved one stays Approved) | Any PUT resets Approved → Pending | Only a real change should need re-approval (R13); pressing Save twice shouldn't cancel the prosumer's QR |
| D33 | 2026-09-28 | Booking search matches the station name, or a reservation id only when the **full 24-character id** is typed | Partial id search | Ids are stored as MongoDB ObjectIds (not text), so "contains" doesn't work on them without slow conversions; people copy/scan whole ids anyway |
| D34 | 2026-09-28 | "Today's reservations" = not Cancelled and starting on **today's Sri Lanka date**; the dashboard's pending table only lists **upcoming** Pending bookings | UTC day; include past Pending | Staff think in local days; a past Pending booking can't be approved (approve needs a future start), so listing it next to an Approve button would only produce errors |
| D35 | 2026-09-29 | **One idempotent deploy script** (`scripts/deploy-api.ps1`, uses IIS's `appcmd`) creates the app pool/site/firewall rule only when missing and republishes every time | Click through IIS Manager for each deploy; Visual Studio publish profile | Repeatable in one command before the viva (and after every fix); `appcmd` ships with IIS, so no extra PowerShell modules are needed; each step is commented so it doubles as the explanation of IIS hosting |
| D36 | 2026-09-29 | Web talks to the **dev API (:5080)** during `npm run dev` and to the **IIS API (:8080)** in the built site (`.env.development` / `.env.production` → `VITE_API_BASE_URL`) | One address for both | Dev work can change and restart the API freely; the hosted demo always uses IIS. No address is hard-coded in the code |
| D37 | 2026-09-29 | Login session kept in **localStorage** and in a React context (`AuthContext`); the fetch wrapper adds the token and **logs out automatically on 401**; expired sessions are dropped on load | Cookies; Redux | Survives a page refresh, simple to explain, no extra packages (Redux is banned); matches the Android app keeping its session in SQLite |
| D38 | 2026-09-29 | With **HashRouter**, in-page jumps (skip link, "How it works") scroll/focus by code instead of `href="#id"` | Normal `#anchor` links | HashRouter uses the `#` part of the address for pages, so `#how` would open a page called "/how" (404) |
| D39 | 2026-09-29 | **One `UserForm` page for web users and prosumers** (`kind="staff"` / `kind="prosumer"`), and one shared `UserTable` for both lists | Separate ProsumerForm / table copies | Both call the same `/api/users` endpoints with almost the same fields; one file is less to maintain and explain (prosumer = role fixed to Prosumer + address field) |
| D40 | 2026-09-29 | Web lists load inside `useEffect` and set state only when the API answers, with a `cancelled` flag; actions ask for a reload with a `reloadKey` | A `load()` function that sets `loading` first and is called from the effect | Follows React's data-loading pattern (no linter warnings) and stops an older, slower answer from overwriting a newer one when filters change quickly |
